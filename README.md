# 🛡️ ScamShield AI

**AI-Powered Scam & Fraud Message Intelligence**

An end-to-end NLP/ML system that classifies free-text messages (SMS, WhatsApp, call transcripts, email) as **SAFE**, **SUSPICIOUS**, or **SCAM/FRAUD**, trained on a Hinglish (Hindi-English code-mixed) cyber-scam dataset, with a full explainability layer and a production-style Flask dashboard.

## Overview

Cyber-enabled financial fraud — fake KYC/bank calls, "digital arrest" police-impersonation scams, courier/parcel scams, lottery scams — is a large and fast-growing problem, frequently conducted in Hinglish over calls and messages. **ScamShield AI** takes an arbitrary message and returns:

- A risk verdict (🟢 SAFE / 🟡 SUSPICIOUS / 🔴 SCAM)
- A calibrated risk score
- Plain-language indicators explaining *why* the message looks risky
- A recommended action

## Problem Statement

Give a user (or a downstream application) an automatic, explainable risk assessment of an incoming message, so they can decide whether to trust it, verify it, or report it. A **missed scam (false negative)** is materially more costly than a false alarm on a safe message — that trade-off explicitly shaped the modelling choices below.

## Key Features

- 🧹 **Leakage-safe data pipeline** — the raw dataset collapses to far fewer distinct messages than rows (see *Dataset* below); the cleaning pipeline explicitly deduplicates on message text before splitting, so reported metrics reflect genuine generalisation, not memorised strings.
- 🔤 **Hinglish-aware NLP pipeline** — word + character n-gram TF-IDF (character n-grams are robust to Hinglish spelling variation), combined with handcrafted scam-indicator features.
- 🤖 **5-model comparison** — Logistic Regression, Linear SVM, Multinomial Naive Bayes, Random Forest, and XGBoost, compared with stratified 5-fold cross-validation and a held-out test set.
- 🎯 **Recall-aware model selection** — models ranked by macro F1 with scam-class recall as an explicit tie-breaker, because false negatives are the costly error here.
- 🧠 **Explainability layer, kept separate from the model** — a rule-based indicator detector (URLs, phone numbers, currency mentions, urgency/financial/authority-impersonation/blackmail keyword groups) explains *why* a message looks risky, without pretending the statistical model "understands intent."
- 🚦 **3-tier risk system from a binary label** — the dataset ships a binary ground truth; predicted probabilities are bucketed into SAFE / SUSPICIOUS / SCAM tiers so borderline messages aren't forced into a binary call (mapping documented below and in `models/model_metadata.json`).
- 🖥️ **Professional dashboard** — analyzer, live risk meter, indicator breakdown, session prediction history, and an analytics panel with charts generated directly from the actual training run.
- 🔌 **Clean REST API** — `POST /api/predict` for programmatic use.
- ✅ **29 automated tests** covering preprocessing, prediction, and the Flask API.

## Dataset

**Source:** `India_Cyber_Scam_Hinglish_Dataset.csv` — 10,000 rows, 8 columns (`text`, `label`, `scam_category`, `caller_type`, `audio_duration`, `urgency_level`, `contains_blackmail`, `language_style`).

**Important data-quality finding:** the raw file has 10,000 rows but only **743 distinct message strings** — a small set of templates repeated many times with different simulated metadata to inflate the row count. If identical strings are allowed into both the train and test split, a model can simply memorise exact text, silently inflating every metric. **The cleaning pipeline explicitly deduplicates on message text before splitting**, so all metrics below reflect the model's performance on genuinely distinct messages, not repeated strings.

| | Raw file | After cleaning (used for modelling) |
|---|---|---|
| Rows | 10,000 | 743 |
| Class balance | 5,000 SAFE / 5,000 SCAM (row-level) | 110 SAFE / 633 SCAM (distinct messages) |
| Exact duplicate rows removed | 378 | — |
| Missing values | 0 | 0 |

**Only the `text` column is used as a model input feature.** `scam_category`, `caller_type`, `audio_duration`, `urgency_level`, and `contains_blackmail` describe how the call was categorised *after the fact* and would not be available for an arbitrary message a real user pastes into the app — they're used only for EDA and error analysis. `language_style` was constant (100% "hinglish") and dropped as uninformative.

### Label → Risk-Tier Mapping

The dataset provides a **binary** ground truth (`0` = legitimate, `1` = scam). The model is trained as a binary classifier on that label. For the product, the predicted scam probability is bucketed into three risk tiers:

| Tier | Condition |
|---|---|
| 🟢 SAFE | predicted scam probability < 0.35 |
| 🟡 SUSPICIOUS | 0.35 ≤ predicted scam probability < 0.65 |
| 🔴 SCAM | predicted scam probability ≥ 0.65 |

This mapping (and the exact thresholds) is also recorded in `models/model_metadata.json`.

## Machine Learning Workflow

1. Load raw data → inspect structure, missing values, duplicates, class balance.
2. Clean: remove exact duplicate rows, drop empty messages, normalise whitespace/HTML, **deduplicate on message text** (see leakage note above), drop the constant `language_style` column.
3. Stratified 80/20 train/test split on the deduplicated data.
4. Fit TF-IDF word (1-2 gram) + TF-IDF char (3-5 gram, `char_wb`) vectorizers and the handcrafted numeric feature extractor **on the training split only**.
5. Train & compare 5 classifiers with 5-fold stratified cross-validation (macro F1).
6. Evaluate every model on the held-out test set: accuracy, precision/recall/F1 (macro, weighted, and scam-class), ROC-AUC, PR-AUC, confusion matrix.
7. Select the final model by macro F1, with scam-class recall as an explicit tie-breaker.
8. Persist the model, fitted vectorizers/scaler, label encoder, and a full metadata JSON (dataset stats, per-model metrics, risk-tier thresholds) — the exact same artifacts are loaded by the Flask app.

## NLP Pipeline & Feature Engineering

- **Word TF-IDF:** 1-2 grams, `max_features=8000`, sublinear TF scaling.
- **Character TF-IDF:** 3-5 grams (`char_wb`), `max_features=8000` — robust to Hinglish spelling variation and obfuscated words (e.g. "0TP").
- **Handcrafted numeric features:** character length, word count, digit count/ratio, uppercase ratio, exclamation/question counts, URL count, phone-number-pattern count, currency-mention count, special-character count, average word length, plus keyword-group hit-counts for **urgency**, **financial**, **account/security**, **authority-impersonation**, and **blackmail** language.
- All three blocks are combined into a single sparse matrix and scaled (`MaxAbsScaler` on the numeric block) — the exact same fitted transformers are reused at inference time (no train/serve skew).

## Evaluation Metrics & Final Model

> Figures below are read directly from the actual training run (`models/model_metadata.json`) at commit time — re-run `python run.py --train` to regenerate them for your environment.

- **Final model selected:** Logistic Regression
- **Test accuracy:** 100.0%
- **Macro F1:** 1.000
- **Scam-class recall:** 100.0%
- **ROC-AUC:** 1.000

**Why results are this high — and what that does and doesn't mean:** the dataset is template-generated (see *Dataset* above); the 743 distinct messages combine a small number of fixed clause fragments ("...se bol raha hoon", "clearance charge ₹499 dena hoga", "OTP turant share kijiye", etc.) that are almost perfectly lexically separable between classes. Even after removing exact-string leakage between train and test, near-perfect scores are a genuine property of this specific dataset's simplicity, not evidence that the model has "solved" scam detection in general. The notebook's error-analysis section runs the trained pipeline against **hand-written messages that are not in the dataset at all** to give a more honest read on generalisation — see *Limitations* below.

## Explainability

Every prediction returns two separate things:
1. **Model prediction** — the statistical model's calibrated scam probability and risk tier.
2. **Heuristic indicators** — a rule-based layer (`detect_indicators()` in `src/feature_engineering.py`) that flags plain-language reasons a message looks risky (e.g. "Urgency / time-pressure language", "Financial / banking request", "Impersonation of police / government authority"). For linear models, `visualizations/top_features.png` also shows the words/n-grams with the largest influence on the model's decision.

These two layers are deliberately kept separate in the API response and the UI — the app never claims the model "understands intent."

## Limitations

- **Small, template-generated training data.** After leakage-safe deduplication, the model was trained on only 743 distinct messages (110 SAFE / 633 SCAM) — a real production system would need a much larger, more diverse, continuously updated dataset of real user-reported messages.
- **Near-perfect in-dataset metrics reflect the dataset's simplicity**, not a guarantee against real-world adversarial scams that don't reuse the templated phrasing seen here (see *Evaluation Metrics* above and the notebook's error-analysis section for out-of-distribution testing).
- **Hinglish/English focus.** The keyword-based explainability layer is tuned for Hinglish + English phrasing common in Indian cyber-scams; it will be less effective on other languages or regional dialects without extending the keyword lists.
- **No guarantee of 100% detection.** ScamShield AI is a decision-support tool, not a substitute for independently verifying suspicious requests for money, OTPs, or personal information.

## Future Improvements

- Collect and incorporate a larger, real-world (anonymised, user-reported) message dataset.
- Add active-learning / continuous retraining as new scam patterns emerge.
- Extend the keyword/explainability lists to more Indian languages.
- Add multi-class scam-category prediction (which type of scam), not just risk tier.
- Add rate limiting and authentication if deployed as a public-facing API.
